### 초기 배치 예시

논리 영역을 0부터 P0, P1, …로 표시한다. 고객의 Page 1은 여기의 P0이다. 각 P는 4KiB다.

```text
             물리 페이지 슬롯 0                 물리 페이지 슬롯 1
CH0       [P0 ][P4 ][P8 ][P12]               [P16][P20][P24][P28]
CH1       [P1 ][P5 ][P9 ][P13]               [P17][P21][P25][P29]
CH2       [P2 ][P6 ][P10][P14]               [P18][P22][P26][P30]
CH3       [P3 ][P7 ][P11][P15]               [P19][P23][P27][P31]
          ← 각 행의 한 묶음이 16KiB →
```

초기 패킹은 다음 식으로 표현한다. 물리 페이지 슬롯은 channel 내부의 임시 번호다. N은 channel당 배치 대상 Plane 수이며 초기값은 8로 확정했다. 구체적인 Die/LUN 구성은 별도 정의한다.

```text
L = floor(byte_address / 4096)
channel = L mod 4
channel_local_index = floor(L / 4)
physical_page_slot = floor(channel_local_index / 4)
offset_in_physical_page = (channel_local_index mod 4) * 4096
                          + (byte_address mod 4096)
plane = physical_page_slot mod N
plane_local_page_index = floor(physical_page_slot / N)
```

확정한 초기값 N=8에서 channel 내부 슬롯 0~7은 각각 Plane 0~7의 첫 페이지로, 슬롯 8은 Plane 0의 다음 페이지로 배치된다. Plane 내부 주소는 아래 확정한 순회 규칙으로 배정한다. 여러 Plane이 준비되어도 같은 channel의 Data 경로는 공유한다. 8개 Plane을 단일 Die에 배정한다는 의미는 아니며 Die/LUN 구성과 추가 공유 제약은 별도 확인한다.

이 식은 초기 배치 생성에만 사용한다. 재배치 후에는 L2P 상태를 조회한다. 경계를 넘는 Read는 필요한 조각으로 분리한다. 물리 페이지 전체를 버퍼에 보관했다면 P0을 위해 읽은 데이터를 P4·P8·P12에도 재사용할 수 있다. NAND 내부 sensing 완료와 controller buffer로 전송 완료는 서로 다른 상태다.

### Plane 내부 물리 주소 생성

사용자 확정 기준은 E/O → SSL → Block → WL → Group 순서다. E/O가 가장 빠르게 변하며, WL만 420에서 0으로 감소한다. Group당 Block 2개, WL 421개, 각 Block의 동일 WL에서 SSL 6개, SSL당 E/O 2개를 사용한다.

```text
q = plane_local_page_index
pages_per_wl_in_group = 2 * 6 * 2 = 24
pages_per_group = 421 * 24 = 10104

group = floor(q / 10104)
r = q mod 10104
wl = 420 - floor(r / 24)
block = floor((r mod 24) / 12)
ssl = floor((r mod 12) / 2)
eo = r mod 2
```

| Plane 내부 페이지 번호 | Group | WL | Block | SSL | E/O | 이전 페이지에서의 전환 |
|---|---|---|---|---|---|---|
| 0 | 0 | 420 | 0 | 0 | 0 | 최초 sensing 20.69μs: 초기 모델 가정 |
| 1 | 0 | 420 | 0 | 0 | 1 | Short |
| 2 | 0 | 420 | 0 | 1 | 0 | Mid |
| 11 | 0 | 420 | 0 | 5 | 1 | 10→11은 Short |
| 12 | 0 | 420 | 1 | 0 | 0 | Mid |
| 23 | 0 | 420 | 1 | 5 | 1 | 22→23은 Short |
| 24 | 0 | 419 | 0 | 0 | 0 | WL과 Block의 자연 순환, Mid |
| 10103 | 0 | 0 | 1 | 5 | 1 | 10102→10103은 Short |
| 10104 | 1 | 420 | 0 | 0 | 0 | Group 전환 |

표의 생략된 페이지도 순서대로 읽었을 때의 분류다. 나열한 행만 건너뛰며 읽는 trace가 아니다. 실제 실행에서는 발행 순서와 L2P 상태에 따라 tR을 다시 판정한다. 이 매핑은 초기 배치 생성 규칙이며, 업데이트로 변경된 L2P를 덮어쓰지 않는다. Group 총개수와 전체 용량은 작업 영역에 맞춰 별도 지정한다.

## 64B 분산 제외 결정

> 사용자 의견: “64B 단위의 분산은 현실적으로 map 정보가 너무 커져서 맞지 않아 보입니다. 그 부분은 제가 커맨트 한 부분을 남겨두고 진행하지 맙시다.”

64B마다 독립 L2P 엔트리를 두면 같은 용량에서 4KiB 관리 대비 엔트리가 64배가 된다. 주소 비트로 계산하는 고정 분산은 반드시 같은 표 용량을 요구하지는 않는다. 이번 제외를 모든 64B 분산 방식이 불가능하다는 결론으로 해석하지 않는다. **64B 저장 분산만 제외하며 고객의 64B Read는 유지한다.**

기존 코드의 lookup을 L2P 변환과 동일시하지 않는다. 데이터 버퍼 검색과 주소 변환의 의미·중첩을 확인해 지연을 중복 계산하지 않는다.

## 같은 물리 페이지의 내부 Read 병합

사용자 승인 기준은 같은 16KiB 물리 페이지를 필요로 하는 여러 Host 요청을 진행 중인 하나의 NAND Read에 연결하는 것이다. 병합 키는 L2P 변환 후의 전체 물리 페이지 식별자이며, 같은 논리 Page 번호나 page offset만으로 병합하지 않는다. 서로 다른 port의 요청도 같은 데이터의 같은 물리 페이지를 가리키면 공유할 수 있다.

이미 대기·발행·sensing·전송 중인 작업이 있으면 새 작업을 중복 생성하지 않고 요청을 연결한다. 해당 작업의 sensing, 전체 페이지 NAND 전송, controller buffer 페이지 공간은 한 번만 소비한다. 페이지의 서로 다른 64B 또는 4KiB 범위를 요구하는 요청도 이 공유 대상에 포함한다. 상태 조회와 작업 등록은 이벤트 처리상 일관되게 수행해 같은 시점의 중복 발행을 막는다.

Host 요청은 병합하지 않는다. 각 요청은 조회 1회와 Outstanding credit 1개를 사용하고, 요청한 데이터 크기만큼 자신의 port로 반환한다. 동일 데이터가 여러 요청에 반환되면 Host 전송량은 각 반환을 포함하지만 NAND 전송량은 공유된 실제 작업 횟수로 집계한다. 응답은 각 port의 in-order 조건을 지킨다.

Prefetch 작업에 Demand가 연결되면 기존 확정된 Demand 승격 규칙을 적용한다. 같은 페이지 작업을 기다리는 요청을 무조건 준비된 buffer hit으로 집계하지 않고, 진행 중 작업 병합으로 구분한다. 병합 수, 실제 sensing 횟수, NAND 전송량, 대기 시간을 함께 기록한다.

이 결정은 진행 중 Read 공유이며 소비 후 캐시 보관을 도입하는 것은 아니다. 데이터 준비 후에도 임시 버퍼가 유효하게 유지되는 동안 도착해 해당 항목에 연결되는 요청은 데이터를 공유한다. 연결된 모든 Host 요청의 반환 완료 시 페이지 공간을 해제한다. 연결된 요청이 남아 있는 상태에서 페이지 공간을 먼저 해제하지 않는다. 향후 실행 중 L2P 업데이트를 도입하면 데이터 세대와 매핑 버전이 다른 요청을 잘못 병합하지 않도록 검증한다.

## 기존 버퍼링 유지와 향후 캐시 검토

사용자 결정: “일단 버퍼링을 그냥 씁시다. 케시 사용 여부는 추후 판단할 수 있게 튜닝 문서에만 반영”. 기존 simulator 파일은 보존하고 새 `znand/` 모듈에서 합의한 임시 버퍼링을 구현한다. LRU는 제안만 있었으며 채택하지 않았다.

사용자는 controller buffer의 초기 용량을 기존 기본값인 전체 공유 8MiB로 확정했다. 이는 8×1024×1024 bytes로, 16KiB 물리 페이지 512개분이다. Port나 channel별 고정 파티션을 두지 않고 활성 port 1~4개 실험에서도 같은 총용량을 유지한다. 용량은 별도 튜닝 변수로 둔다. 이 예산은 현재 데이터 버퍼 모델 기준이며 L2P·요청 descriptor 등 메타데이터의 실제 메모리 비용까지 포함한다고 가정하지 않는다.

현재 코드의 버퍼 동작은 다음과 같다. NAND 발행 전에 페이지 공간을 예약하고, 기본 16KiB 전체 전송과 ECC 후 Host에 반환한다. 해당 페이지의 모든 burst 반환이 끝나면 공간을 해제한다. 기본 64B burst에서는 256개 반환에 해당한다. 이는 임의의 첫 64B 사용 직후 해제하는 정책도, 소비 후 계속 보관하는 LRU 캐시도 아니다. Deep 모델에는 잘못된 Prefetch를 준비 완료 시 폐기하는 별도 경로도 있다.

고객의 부분 읽기 trace로 확장할 때는 전체 페이지가 끝내 소비된다는 현재 가정을 그대로 적용할 수 없다. 부분 Read의 해제 기준은 아래와 같이 확정했다. 미사용 Prefetch는 아래 공간 부족 시 정리 규칙을 따르며 소비 후 캐시 보관은 도입하지 않는다.

### 부분 Read에서의 임시 버퍼 해제

사용자 확정 기준은 controller buffer 항목에 연결된 모든 Host 요청의 마지막 데이터 반환이 끝나면 해당 물리 페이지의 공간을 해제하는 것이다. 16KiB 전체를 Host가 읽었는지는 해제 조건이 아니다. 예를 들어 64B 요청 하나만 연결되어 있다면 그 요청 반환 완료 후 16KiB 공간을 해제한다. 여러 port의 요청이 연결되어 있다면 모두 완료될 때까지 유지한다.

버퍼가 유지되는 동안 새로 연결된 같은 물리 페이지 요청은 기존 데이터를 공유하고 수명에 포함된다. 반환 완료 후 미래 재방문을 기대하며 보관하거나 유예 시간을 추가하지 않는다. 진행 중 NAND 전송이나 연결된 응답에 필요한 데이터를 조기에 해제하지 않는다. 같은 시각의 새 요청 연결과 최종 반환 완료는 결정적인 이벤트 순서로 처리하고 그 규칙을 구현 시 명시한다.

아직 Host 요청이 한 번도 연결되지 않은 Prefetch 항목을 '연결 요청 0개'라는 이유만으로 즉시 해제하지 않는다. 공간이 충분하면 유지하고, 공간이 부족하면 아래 적재 완료 순서 기반 정리 규칙을 적용한다. 초기에는 별도 TTL을 두지 않는다. 미래 정답을 미리 알아 미사용 항목을 즉시 폐기하는 정책도 자동 채택하지 않는다.

Controller buffer 해제는 NAND page buffer를 무효화하지 않는다. Plane당 page buffer에 동일 물리 페이지가 유효하면 재요청 시 재sensing 없이 NAND에서 controller로 전송할 수 있다. 이 경우에도 Data 경로와 controller 공간은 필요하며 출력 명령·ECC 등 세부 비용은 별도 정의한다. 같은 Plane에서 다른 페이지 sensing으로 내용이 교체되면 이후 재방문에는 새로운 sensing이 필요하다.

이 기준은 새 고객 trace를 위한 설계 계약이다. 기존 코드의 '페이지 전체 burst 반환 후 해제' 로직 자체는 보존하고 새 모듈에서 연결 요청 완료 기준을 구현·검증한다.

### 선두 Demand용 공간 보호

사용자 확정 초기값은 활성 port당 16KiB 한 페이지분이다. 활성 port 수 1·2·3·4에서 보호 예산은 각각 16·32·48·64KiB이며, 이는 전체 공유 8MiB 안에 포함된다. 별도 용량을 더하거나 전체 버퍼를 port별로 분할하지 않는다. 보호 규모는 향후 튜닝 가능하게 둔다.

각 port의 가장 앞선 미완료 요청에 필요한 페이지 공간을 확보할 수 있도록 admission을 제한한다. Prefetch와 후속 Demand의 신규 할당이 아직 충족되지 않은 선두 요청의 예약분을 소비하지 않도록 한다. 선두 페이지가 이미 할당되었거나 진행 중 Read에 병합되는 경우 동일 공간을 중복 할당하지 않는다. 두 port의 선두가 같은 페이지를 공유하는 경우에도 실제 점유는 한 페이지로 계산한다.

선두 요청 완료 시 다음 선두의 진행 가능성을 다시 평가한 뒤 후속·Prefetch 할당을 허용한다. 연결 요청 전체 반환까지 페이지를 유지하는 정책과 병합 정책 때문에, 이전 선두가 완료되어도 그 페이지가 후속 요청에 의해 남아 있을 수 있다. 따라서 16KiB 예산을 한 번 예약했다는 이유만으로 교착 방지가 검증되었다고 하지 않는다. 구현 시 선두 교체, port 간 공유, 후속 요청의 페이지 고정 조건에서 진행성을 검증하고 필요하면 보호 공간을 늘리거나 발행·병합 허용 조건을 추가 정의한다.

초기 4KiB 정렬 요청은 위 배치에서 한 물리 페이지 안에 들어간다. 향후 비정렬·경계 횡단 요청이 여러 물리 페이지를 동시에 요구하면 필요한 보호 예산을 재검토한다.

### 미사용 Prefetch의 공간 회수

사용자 승인 기준은 공간 부족 시 Host 요청이 연결되지 않고 적재가 완료된 Prefetch 항목 중 오래된 것부터 폐기하는 것이다. 초기 구현 기준에서 적재 완료 시점은 NAND 전송과 현재 모델의 ECC 처리까지 완료되어 ready가 된 시각으로 정의한다. 동시 완료 항목은 고정 순번으로 선택한다. 이는 미사용 적재 순서 기준이며 소비 후 데이터에 적용하는 LRU 캐시를 도입하는 것이 아니다.

필요한 페이지 공간을 확보할 때까지 회수 가능한 항목을 순서대로 정리한다. NAND 명령·sensing·전송·ECC 진행 중인 항목이나 Host 요청이 연결된 항목은 회수하지 않는다. 회수 직전 적격성을 다시 확인하여 Demand가 연결된 데이터를 버리지 않는다. 폐기해도 이미 발생한 NAND 비용과 전송량은 결과에 남긴다. Controller 항목 폐기만으로 NAND page buffer는 무효화하지 않는다.

공간이 충분하면 미사용 Prefetch를 유지한다. 미래 접근 여부를 미리 알아 폐기하지 않는다. 회수 가능한 항목이 없으면 새 NAND 작업은 공간 확보까지 대기한다. 선두 Demand 진행을 보호하기 위해 아래 활성 port당 16KiB 예약 기준을 적용한다. Prefetch뿐 아니라 후속 Demand의 신규 할당에도 미충족 선두 예약 보호를 적용한다. 단순히 Host 요청이 없는 Prefetch를 모두 즉시 폐기하는 정책은 사용하지 않는다.

평가에는 폐기 페이지 수, 폐기까지의 보관 시간, 폐기 후 재요청 수, 공간 부족 대기 시간을 기록한다. 종료 시 남은 미사용 항목은 실행 중 폐기와 구분해 집계한다.

향후 캐시를 검토한다면 다음 네 조합을 후보로 둔다. 현재 단계에서 실행하기로 확정한 실험은 아니다.

| Controller cache | Prefetch | 향후 비교 목적 |
|---|---|---|
| OFF | OFF | Demand 기준 |
| ON | OFF | 소비 후 데이터 재사용 효과 |
| OFF | ON | 사전 준비 효과 |
| ON | ON | 사전 준비와 재사용의 결합 |

Cache OFF라도 전송·Prefetch 대기용 임시 버퍼는 필요하다. ON 후보 정책은 LRU이며, 전송 중이거나 응답에 필요한 항목의 보호, 미사용 Prefetch의 우선순위를 추가로 정해야 한다. 두 조건에서 총 데이터 버퍼 예산을 맞춘다. NAND의 Plane당 page buffer는 controller cache ON/OFF와 별개로 유지한다. 항상 hit이라고 가정하지 않고 실제 보관 상태를 판정한다.

활성 port 1·2·3·4 실험에서는 NAND channel을 항상 4개로 유지한다. 전체 요청량을 고정해 port에 나누는 실험과 port당 요청량을 고정해 총부하를 늘리는 실험을 구분한다.

## 고객 Read 패턴

| 패턴 | 논리 Page 순서 | 요청 크기 |
|---|---|---|
| A-1 | 1→2→3→… | 각각 4KiB |
| A-2 | 1→3→2→… | 각각 4KiB |
| B-1 | 1→2→3→… | 각각 64B |
| B-2 | 1→3→2→… | 각각 64B |
| B-3 | 1→3→1→2→… | 각각 64B |

B-3는 같은 논리 Page를 재방문할 때 이전과 다른 64B 위치를 읽는다. 구체적 offset과 B-1/B-2의 offset은 추가 정의한다. 다른 offset이 반드시 다른 NAND 물리 페이지를 뜻하지는 않는다. 짧은 예시 순서를 무한 반복하면 데이터가 과도하게 캐시에 상주하므로 작업 영역 크기와 재방문 거리도 지정한다. 4KiB와 64B 요청은 유효 데이터량이 다르므로 요청 건수만으로 성능을 비교하지 않는다.

## SCA와 Plane 자원 사용 기준

사용자 확정 사항: 4개 NAND channel 각각에 독립적인 명령·주소(CA) 경로와 Data 경로가 있다. 같은 channel에서도 CA와 Data 전송은 중첩할 수 있다. 하나의 channel Data 경로를 사용하는 데이터 전송끼리는 중재가 필요하다.

Plane당 page buffer는 하나다. 동일 Plane에서 현재 물리 페이지의 필요한 데이터를 전송하는 동안 다음 물리 페이지의 sensing을 시작하지 않는다. 다음 sensing은 해당 NAND 데이터 전송이 완료된 뒤 시작한다. 이는 Host 반환 완료까지 기다린다는 의미는 아니다. 기존 controller 버퍼링의 전체 페이지 전송 기준에서는 16KiB NAND 전송 완료가 이 경계다. 부분 전송을 도입할 경우에는 필요한 전송 범위를 별도로 정의한다.

다른 Plane의 sensing과 데이터 전송은 병렬 진행할 수 있지만, 공통 channel의 CA/Data 경로 및 기타 공유 자원 제약은 적용한다. CA 경로가 비어 있다는 사실만으로 대상 Plane의 sensing을 즉시 시작하지 않는다. 초기 모델에서는 사용 중인 Plane의 요청을 controller 대기열에 남겨 두고 다른 Plane의 발행 가능한 요청을 탐색한다. NAND 측 Busy Plane 명령 선접수 큐는 도입하지 않는다.

```text
동일 Plane A: sensing P0 → P0 데이터 전송 → sensing P1 → P1 데이터 전송
다른 Plane B:       sensing Q0 ─────────→ Q0 데이터 전송
```

그림은 동작 순서 예시이며, 같은 channel에서 P0와 Q0의 데이터 전송은 겹치지 않는다. Page buffer의 데이터는 전송 완료만으로 자동 소멸한다고 가정하지 않는다. 이후 같은 Plane의 다른 페이지 sensing에 의해 교체되는 상태를 추적해야 한다.

### Channel CA 명령 중재

사용자 승인 초기값은 NAND Read 명령 하나당 CA 점유 100ns(0.1μs)다. 기존 `command_us=0.1`을 초기값으로 채택한 모델 가정이며 SCA 실측·규격값으로 확정하지 않는다. 같은 channel의 CA 전송은 직렬화하고 다른 channel의 CA 및 Data 경로와는 독립적으로 진행한다. 단일 NAND Read 동작의 초기 시간 구성은 CA 전송 → sensing(tR) → Data 전송으로 둔다. 100ns는 tR 또는 Data 전송 시간에 포함되지 않는다.

기존 command 지연을 그대로 더하고 CA 100ns를 추가하는 이중 계산을 피한다. 실제 구현에서는 기존 command 지연의 역할을 이 CA 점유로 대응시킨다. NAND sensing이 필요 없는 버퍼 적중 경로에 100ns를 일괄 부과하지 않는다. NAND page buffer에서 데이터를 꺼내는 별도 명령 등 상세 프로토콜 비용은 이 Read 명령 가정만으로 확정하지 않는다.

CA 경로가 사용 가능해지면 대상 Plane과 controller buffer 등 발행에 필요한 자원이 확보되는 요청을 후보로 삼는다. 후보 중 Demand를 우선하고, 없으면 Prefetch를 선택한다. 같은 등급에서는 CA 대기열에 들어온 순서를 사용하며 동시 도착은 고정 순번으로 결정한다.

사용 중인 Plane의 요청은 제거하지 않고 대기열에 유지하며 다른 Plane의 발행 가능한 요청을 처리한다. 모든 Demand가 발행 불가능한 상황에서는 발행 가능한 Prefetch를 진행할 수 있다. 이 규칙은 channel별로 적용하고 Host 응답 ordering은 별도로 유지한다.

Prefetch 대기 요청에 Demand가 연결되면 우선순위를 Demand로 승격하되 원래 대기 순번을 유지한다. 같은 작업을 중복 발행하지 않는다. 이 승격 처리는 Data 경로의 Demand 분류와 일관되게 구현한다. 발행 이후 sensing은 해당 Plane의 주소 이력과 사용 제약을 따른다.

### Channel Data 전송 중재

각 channel의 Data 경로가 비면 해당 경로에서 전송 가능한 준비된 데이터 중 Host의 미완료 요청이 기다리는 Demand를 먼저 선택한다. 그런 Demand가 없으면 아직 Host 요청이 없는 Prefetch를 선택한다. 동일 우선순위에서는 데이터가 전송 준비된 시점이 빠른 순서를 사용하고, 동시 준비 시에는 재현 가능한 고정 순번으로 결정한다.

Prefetch로 시작했더라도 Data 전송 선택 전에 Host 요청이 붙으면 Demand로 분류한다. 구현 시 기존 준비 시점은 유지하고 중복 NAND 작업을 만들지 않는다. 아직 sensing 중인 Demand 때문에 전송 가능한 Prefetch까지 무조건 대기시키지는 않는다.

이미 시작한 Data 전송은 더 높은 우선순위 요청이 도착해도 중단하지 않는다. 현재 전체 페이지 전송 기준에서는 16KiB 전송 완료까지 유지한다. 같은 channel의 다른 Plane 데이터는 그 후 중재하며, 다른 channel은 독립적으로 진행한다. Data 경로는 준비 시점 순서, CA 경로는 대기열 진입 순서라는 차이가 있다. Host 반환 순서는 별도 조건을 따른다.

Demand가 계속 대기하는 부하에서는 Prefetch가 오래 기다릴 수 있다. 초기에는 이 우선순위를 유지하고, 평가 시 등급별 대기 시간과 Prefetch 진척을 기록한다. Aging이나 대역폭 할당은 향후 튜닝 후보이며 현재 도입하지 않는다.

이 절은 모델링 계약이며 SCA 상세 프로토콜 구현 완료를 뜻하지 않는다. Host의 Outstanding과 요청 발행 간격은 NAND SCA와 별도로 결정한다.

## NAND 지연 판정

| 물리 주소 전환 | 문서의 기본 분류 |
|---|---|
| 인접 E/O | Short |
| 인접 SSL 또는 BLK | Mid |
| 정의된 WL과 BLK의 자연스러운 순환 | Mid |
| 같은 BLK 내 WL 변경 또는 비연속 점프 | Long |
| Group 변경 | 1st Long + tRRC = 20.69μs |

논리 Page 번호만으로 판정하지 않는다. L2P 변환 후 실제 NAND 발행 순서로 판정한다. 각 Plane의 최초 sensing은 20.69μs로 확정했다. 이후 주소 전환의 tR 상태도 Plane별로 유지하기로 확정했다. Page buffer 내용이 유효하지 않은 상태에서 동일 페이지를 재sensing하는 예외 규칙은 별도 확인한다. 전체 port가 공유하는 이전 주소 하나로 판정하지 않는다.

원래 tR을 이벤트에 입력하고 Array와 전송의 실제 중첩으로 노출 지연을 계산한다. tR에서 전송 시간을 먼저 빼고 이벤트에서도 겹치는 이중 은닉을 피한다. WL Jumping은 문서의 기본 비활성 조건을 초기안으로 삼고, 도입 시 전후 6페이지 등의 조건을 확인한다.

문서의 4channel×8plane×16KiB=512KiB는 병렬 합계량이다. 각 64B 요청이 반드시 512KiB 읽기를 발생시킨다고 가정하지 않는다. Plane 수와 내부 연결은 현재 코드의 자원 모델과 대응시킨 뒤 적용한다.

### Plane별 주소 이력

각 `(channel, plane)`이 자신의 직전 sensing 물리 주소 `(group, wl, block, ssl, eo)`를 기억한다. 이후 Die/LUN 구조를 명시한다면 식별 키에도 해당 계층을 포함한다. 다음 sensing의 tR은 해당 Plane의 이력과 대상 주소를 비교해 판정한다. 다른 Plane의 Read나 요청 port 변경은 이력을 변경하지 않는다.

Host 요청 순서가 아니라 실제 NAND sensing 순서를 사용한다. 구현 시 sensing 시작에 이전 주소로 지연을 판정하고, 완료 시 해당 주소를 마지막 완료 sensing 주소로 기록한다. 동일 Plane에서 sensing을 직렬화하므로 다음 sensing은 완료된 이력을 사용한다. Demand와 Prefetch 모두 실제 sensing을 수행하면 이력을 갱신한다.

Controller buffer에서 응답하거나 이미 유효한 NAND page buffer의 다른 offset을 전송하는 경우는 새로운 sensing이 아니므로 이력을 갱신하지 않는다. Page buffer의 유효 데이터와 마지막 sensing 주소는 별도 상태로 관리한다. 데이터 전송 중 동일 Plane의 다음 sensing을 시작하지 않는 제약도 유지한다.

### 최초 Read 지연 가정

각 Plane이 초기 NAND 읽기 상태에서 처음 수행하는 sensing에는 1st Long 17.52μs와 tRRC 3.17μs를 합한 20.69μs를 적용한다. 이는 문서에 최초 Read 조건이 명확하지 않은 상황에서 사용자가 승인한 초기 모델 가정이며, 제품 측정값으로 확정하지 않는다. 최초 sensing 지연은 별도 파라미터로 조정할 수 있도록 설계한다.

최초 여부는 port가 아니라 Plane별로 추적한다. Demand 또는 Prefetch 중 먼저 실제 sensing을 수행하는 동작에 적용하며, 같은 Plane을 다른 port가 처음 이용한다고 다시 부과하지 않는다. 독립적인 cold 실행 시작 시 초기화한다. Warmup 뒤 측정만 시작할 때에는 NAND 상태를 유지하며 최초 비용을 재부과하지 않는다. Controller buffer miss 자체가 최초 상태를 뜻하지도 않는다. 이 세부 상태 처리는 위 가정을 일관되게 적용하기 위한 구현 기준이다.

## 요청 조회 초기 기준

사용자 승인 기준은 기존 lookup 구조와 조회당 500ns(0.5μs)를 유지하는 것이다. 현재 multiport 기본 설정은 Port별 500MHz lookup clock, 파이프라인 2개, 각 파이프라인 initiation interval 1 cycle, 동시 lookup slot 500개다. 이는 코드의 초기 설정이며 제품 실측값이 아니다. 조회 latency와 처리율을 분리해 기록하고 조정한다.

기존 코드에서는 Host burst 하나마다 조회를 수행하며 기본 burst는 64B다. 고객 패턴에 적용할 기준은 64B와 4KiB 모두 논리 요청 하나당 조회 1회, Outstanding credit 1개로 확정했다. 4KiB를 64개의 독립적인 64B 요청으로 분할하지 않는다.

| Host 요청 크기 | 조회 횟수 | Outstanding 점유 | 512bit 반환 beat 수 | 순수 반환 시간 |
|---|---|---|---|---|
| 64B | 1회 | 1개 | 1 | 1ns |
| 4KiB | 1회 | 1개 | 64 | 64ns |

표의 반환 시간은 1GHz에서 stall과 beat 사이 간격이 없는 경우다. 조회 서비스 지연은 두 크기 모두 500ns이며 큐 대기는 별도다. Outstanding credit은 해당 요청의 마지막 데이터 반환 완료 시 해제한다. 내부 L2P나 NAND 동작이 여러 조각으로 나뉘더라도 Host 요청 수와 credit을 그 조각 수만큼 늘리지 않는다. 폭 변경 시 beat 수는 요청 bytes를 beat bytes로 나눈 올림으로 계산한다. Port 내부 strict in-order 조건에 따라 앞선 요청의 마지막 beat를 반환한 뒤 다음 요청의 반환을 시작한다. 서로 다른 요청의 응답 beat를 같은 port에서 인터리빙하지 않는다.

64B와 4KiB를 같은 Outstanding 개수로 비교하면 대기 중인 총 요청 bytes가 다르다. 포화 탐색 결과에 요청 개수와 in-flight bytes를 함께 기록하고, 필요하면 같은 in-flight bytes 조건의 보조 비교를 둔다. 기존 코드의 64B 기본값과 이 요청 단위 계약의 차이는 구현 단계에서 반영한다.

500ns 동안 다른 조회를 시작할 수 없는 직렬 구조가 아니다. Port별 두 파이프라인을 통해 여러 조회를 겹치되 clock edge 대기·queue·slot 제한을 적용한다. 조회 대기 중인 Host 요청도 기존 구현에 따라 Outstanding을 점유한다. Outstanding sweep에서는 lookup slot 제한도 함께 관측하며, 조회 지연과 큐 대기를 별도로 출력한다.

기존 lookup을 실제 L2P 변환 지연으로 확정하지 않는다. 향후 L2P 비용을 상세 도입할 때 기존 500ns와 포함 관계를 정의해 중복 가산을 피한다. NAND Prefetch의 선행 발행 경로와 Host 요청 조회 경로도 구분한다. 이 구조는 새 `znand/` 모듈에 반영하며 기존 모듈은 보존한다.

## Port 내부 응답 순서

사용자 필수 조건은 port 내부 in-order다. 각 port에서 수락된 요청에 순번을 부여하고 그 순서대로 반환한다. 같은 port의 서로 다른 AXI ID도 이 순서 제약을 우회하지 않는다. 다른 port의 같은 숫자 ID는 독립이며 port 간 전역 FIFO를 만들지 않는다.

앞선 요청 A의 데이터가 준비되지 않으면, 뒤의 B가 준비됐더라도 그 port의 반환은 기다린다. A의 마지막 beat 반환 후 B를 반환하며 요청 간 beat 인터리빙은 하지 않는다. 내부 lookup·NAND 발행·완료는 기존 자원 중재에 따라 순서가 바뀔 수 있으나, Host 반환에서는 port별 순번을 지킨다. Outstanding은 각 요청의 마지막 반환까지 점유한다.

평가 시 선두 요청의 미준비 때문에 후속 준비 요청이 기다리는 Head-of-Line 대기 시간을 port별로 기록한다. Port 내부 out-of-order 반환은 이번 튜닝 후보에 포함하지 않는다. 실행 중 실제 순서 준수도 검증한다. 데이터 준비 전에 항상 반환 가능하다고 가정하지 않는다.

## Host 반환 대역폭 기준

사용자 확정 초기값은 port당 512bit와 1GHz다. 매 사이클 유효 데이터 한 beat를 반환할 때 이론상 `512 / 8 * 10^9 = 64GB/s`이며, 활성 port 1·2·3·4개의 합산 상한은 각각 64·128·192·256GB/s다. 실제 처리량은 데이터 준비·ordering·요청 공급·stall 등으로 더 낮아질 수 있다. 이는 모델의 AXI 반환 경로 설정으로, UCIe 링크 실효 대역폭을 검증한 값은 아니다.

한 port도 네 NAND channel의 데이터를 읽을 수 있지만 Host 반환 속도가 네 channel의 합산 속도로 증가하는 것은 아니다. NAND 명목 합산 320.45GB/s와 Host 합산 256GB/s를 구분한다. 유효 데이터가 충분히 준비되는 조건에서 Host 포화가 먼저 나타날 수 있으며, NAND의 tR·읽기 증폭 등으로 더 이른 병목이 생길 수도 있다.

폭과 클록은 별도 튜닝 변수로 두며 변경 시 beat 수와 정수 사이클 소요를 반영한다. 64B와 4KiB 요청의 기존 512bit 기준 순수 반환 시간은 각각 1ns와 64ns다. 폭·클록 변화가 기존 코드의 AR 발행 속도와 공유 설정으로 연결되는지도 점검하여 반환 경로 변화만으로 결과를 설명하지 않는다.

## NAND Data 대역폭 기준

사용자 승인 초기값은 4개 channel 합산 320.45GB/s이며, 각 channel은 80.1125GB/s로 균등 배분한다. GB는 10^9 bytes, KiB는 1024 bytes 기준이다. Channel에 연결된 8개 Plane은 이 Data 경로를 공유하며 Plane별로 80.1125GB/s를 각각 부여하지 않는다. Port별 예약 대역폭으로도 나누지 않는다.

순수 Data 전송 시간은 `전송 bytes / (80.1125 * 1000)` μs다. 16KiB 한 페이지는 약 0.204512μs이며, 한 channel에서 8개 페이지를 직렬 전송하면 약 1.636099μs다. 네 channel에서 같은 전송을 병렬 수행하면 총 512KiB의 순수 전송 시간이 약 1.636099μs가 된다. 이 계산은 CA·tR·대기·turnaround·ECC·Host 반환 시간을 포함하지 않는다.

기존 모델의 `io_gbps`는 페이지 전송 계산에서 channel별 속도로 사용되므로 연결 시 80.1125로 대응시켜야 한다. 기존 모듈은 보존하고 새 모듈의 channel 전송 속도에 적용한다. 추가 전송 오버헤드가 있다면 명목 Data 속도와 구분해 기록한다. Plane 가용 시간 85%는 별도 자원 점유 모델로 반영하며 이 전송 속도에 다시 곱하지 않는다.

## 내부 작업에 따른 Plane 가용 시간

사용자는 Utilization을 GC 등 NAND 내부 작업에서 발생하는 비효율로 설명했으며, 초기에는 Plane별 가용 시간 85%로 근사하기로 확정했다. 각 Plane 시간의 15%를 내부 작업 점유 목표로 두어 Host Read와 Prefetch의 NAND 자원 접근을 제한한다. 이는 제품의 측정된 GC 일정이 아니라 모델 가정이다.

- tR 자체와 CA·Data 전송 속도는 유지한다. 결과 처리량에 0.85를 다시 곱하지 않는다.
- 점유된 Plane의 요청은 대기하고, 다른 Plane의 발행 가능한 요청은 기존 중재 규칙에 따라 진행한다. 이 점유는 Prefetch에도 동일하게 적용한다.
- 점유 구간 길이, 주기 또는 분포, Plane별 시차와 동시 점유 정도, seed는 별도 튜닝 변수다. 85%만으로 점유 일정을 결정할 수 없다.
- 주기형 예시에서는 주기 T 중 0.15T가 점유 시간이다. 특정 T는 아직 확정하지 않았다. 짧은 반복 점유와 긴 연속 점유는 같은 비율이어도 지연에 다른 영향을 줄 수 있다.
- 비선점 NAND 동작과 점유 구간 경계가 겹칠 때의 처리 규칙은 구현 전에 결정한다. 진행 중 전송을 임의로 중단하지 않으며, 목표 점유율과 실제 점유율을 별도로 기록한다.
- 내부 작업 중 NAND page buffer 접근 가능 여부와 내용 무효화 여부도 별도 결정한다. 가용률 계수만으로 버퍼 내용을 임의로 삭제하지 않는다. Controller buffer에서 제공 가능한 데이터까지 일괄 정지시키지 않는다.

다른 Plane으로 작업을 돌릴 수 있으므로 Plane 가용률 85%가 전체 대역폭 85%를 보장하지 않는다. 실제 내부 작업 점유 시간, 그로 인한 대기, channel 활용률, 응답 지연과 처리량을 함께 보고한다. 초기 근사는 GC의 데이터 이동, CA/Data 점유, L2P 갱신을 상세 재현하지 않는다.

후속 상세 GC 모델에서는 내부 Read·Program·Erase·데이터 이동이 실제 자원을 점유하도록 구현한다. 동일한 내부 작업을 이벤트로 반영한 경우 해당 비효율을 15% 점유로 중복 적용하지 않는다. MQSim에서 배치 snapshot만 가져오는 것은 실행 중 GC 자원 점유까지 가져오는 것이 아니므로 두 항목을 구분한다.

## MQSim 사전 상태 연동

MQSim의 preconditioning은 workload 통계 등을 바탕으로 사전 상태를 구성한다. 실측 L2P나 쓰기 이력 전체를 재생한 결과와 동일시하지 않는다. [MQSim FTL 구현](https://github.com/CMU-SAFARI/MQSim/blob/master/src/ssd/FTL.cpp)

제안하는 방식은 사전 조건화 이후 L2P와 유효 페이지 상태를 추출하고 geometry를 검증한 뒤 변환하는 것이다. 표준 출력에서 즉시 가져올 수 있다고 검증된 기능은 아니며, 추출·변환 코드가 필요하다.

- 처음에는 가져온 배치를 고정하고 Read와 Prefetch를 비교한다. 실행 중 업데이트·GC 경합은 후속 범위다.
- 논리 공간, 점유율, 사용 이력 조건을 맞춘다. 각 배치 방식의 실제 물리 매핑은 서로 달라진다.
- MQSim 배치를 재패킹했다면 변환한 배치임을 표시하고 원본 배치를 유지한 경우와 구분한다.
- MQSim의 NVMe 응답 시간이나 일반 NAND 지연을 zNAND 성능값으로 그대로 사용하지 않는다.
- 누락, 범위 초과, 의도하지 않은 물리 영역 중복, 부분 페이지 유효 범위를 검사한다.

## Prefetch 정확도 평가

사용자 확정 사항은 미래 요청을 아는 합성 Prefetch의 정확도 100%를 이상적인 예측 기준선으로 사용하고, 정확도를 낮춘 조건도 비교하는 것이다. 이는 실제 예측 알고리즘의 달성 정확도를 측정한 결과가 아니다. 100%도 발행 지연·버퍼 부족·경합 때문에 늦게 도착하거나 사용 전에 폐기될 수 있으므로 항상 적중 또는 최대 처리량을 보장하지 않는다. Prefetch OFF 기준도 유지한다.

정확도 구간은 아직 확정하지 않았다. 구현 전 다음을 구분해 정의한다.

- 입력 정확도는 합성 후보 중 미래 수요 대상이 되도록 생성한 비율이다. 후보 생성 수·실제 발행 수·병합 또는 억제 수를 따로 기록한다.
- 실현 유용성은 실제 발행한 Prefetch가 추후 Demand에 사용된 비율이다. 진행 중 병합으로 일부 기다린 경우와 미리 준비되어 대기를 없앤 경우를 구분한다.
- Coverage는 전체 Demand 중 Prefetch가 도움을 준 비율이다. 정확도와 동일하지 않다.
- Timeliness는 해당 데이터가 필요할 때 준비됐는지다. 정확도와 선행 시간은 별도 실험 축이다.

초기 민감도 실험에서는 동일한 총 후보 예산과 선행 시간 조건에서 정답 후보 일부를 오예측 후보로 바꾸는 방식을 제안한다. 정확도만 낮추면서 전체 발행량까지 임의로 증가시키지 않는다. 오예측 후보는 실제 물리 주소를 가지며 정상적인 CA·Plane·Data 자원과 controller buffer를 사용해야 한다. 정답 여부를 알아 준비 완료 즉시 폐기하지 않고 확정한 공간 부족 시 정리 정책을 적용한다.

기존 Deep 모델은 미래 trace를 알고 있으며 잘못된 Prefetch를 ready 시 즉시 폐기하는 경로가 있으므로, 기존 accuracy 옵션을 그대로 실행한 결과를 위 정책을 구현한 결과로 취급하지 않는다. 향후 구현에서는 오예측 주소가 Demand 또는 다른 Prefetch와 우연히 겹치는 경우도 실제 주소 기준으로 처리하고, 입력 정확도와 관측 유용성을 각각 보고한다.

오예측 주소의 분포·channel 편향·작업 영역과의 관계는 아직 미결정이다. 이러한 조건은 오예측의 자원 경합 정도를 바꾸므로 seed와 함께 저장한다. 동일 설정을 반복해 결과 편차를 보고하고, 미사용 전송량·퇴거량·Demand 대기·유효 대역폭을 비교한다.

## Port별 workload 영역 구성

사용자 확정 범위는 비중첩 데이터 영역과 일부 중첩 데이터 영역을 모두 평가하는 것이다. 활성 port 1~4개와 전체 요청량 고정·port당 요청량 고정 실험에 각각 적용한다. 활성 port가 하나일 때 port 간 겹침은 해당하지 않는다. 각 port 안에서는 고객 패턴의 순서와 in-order 응답을 유지한다.

| 유형 | 구성 | 확인할 효과 |
|---|---|---|
| 비중첩 | Port별로 서로 다른 논리 영역을 읽음 | 독립 workload의 대역폭·channel 병렬성·공유 자원 경합 |
| 일부 중첩 | Port별 고유 영역과 공통 영역을 함께 읽음 | 같은 물리 페이지의 진행 중 Read 병합·임시 버퍼 공유 |

논리 영역이 다르더라도 같은 channel이나 Plane을 이용할 수 있으므로 비중첩을 무경합으로 해석하지 않는다. 의도적으로 독립 물리 페이지를 평가하는 기준선에서는 물리 페이지 내부의 서로 다른 4KiB 조각만 나누어 겉으로 비중첩처럼 보이지 않도록 L2P 결과를 확인한다.

일부 중첩의 비율, 공통 영역 크기, 요청 시간차는 별도 튜닝 변수다. 같은 데이터 영역을 읽는 것만으로 병합이 보장되지 않는다. 실제 진행 중 작업이나 유효한 임시 버퍼가 있는 시점에 요청이 도착해야 공유할 수 있다. 같은 물리 페이지의 같은 offset과 다른 offset 접근도 구분해 기록한다.

비교에서는 총 요청 bytes·요청 수와 중복을 제외한 고유 논리 데이터량을 함께 기록한다. Host 반환 bytes는 각 요청의 반환을 모두 포함하고, 실제 NAND sensing·전송 횟수는 병합 후 작업을 센다. 같은 seed와 요청 타이밍 조건으로 배치 후보를 비교하고, channel 부하 편향과 중첩 시점 차이를 결과에 명시한다. 구체적인 중첩 비율과 발행 시간차는 아직 확정하지 않았다.

## 실험 순서와 평가 지표

### 최대 처리량 구간 탐색

사용자 확정 사항: 요청 동시성은 단순한 1 대 다수 비교를 넘어 최대 성능이 나오는 구간까지 평가한다. 활성 port 수 1·2·3·4 각각에서 Port별 Outstanding을 증가시킨다. 균등 설정일 때 전체 상한은 활성 port 수와 Port별 상한의 곱이며, 실제 동시 처리 수는 별도로 기록한다.

탐색 절차는 1, 2, 4, 8, …처럼 넓게 탐색한 뒤 성능 증가가 둔화하는 구간을 세분화하는 방식으로 한다. 최대 처리량 탐색에서는 요청 공급 부족이 병목이 되지 않도록 충분한 작업량을 제공하되, 실제 발행 경로의 속도 제한은 유지한다. 각 비교점에서 배치·버퍼·tR·Prefetch 설정을 고정한다.

포화 판정은 여러 연속 증가점의 처리량 개선 폭과 반복 실행 편차를 함께 보고 결정한다. 세부 임계값은 실행 계획에서 명시한다. 결과에는 관측 최대 유효 대역폭, 최대값의 95%에 처음 도달한 Outstanding, 해당 지점의 평균·p95·p99 지연, 실제 동시 처리 수와 병목 자원을 기록한다. 95% 지점은 실용적인 동시성 지표이며 포화 자체의 증거와 구분한다.

Host 반환 경로·lookup·CA/Data·Plane·버퍼 중 어디에서 제한되는지 확인한다. 추가 Outstanding에서 처리량은 유지되고 대기 지연만 증가하는 구간도 포함한다. 자원 또는 실행 예산 한계로 탐색을 중단했다면 탐색 상한에서 관측한 성능으로 표시하고 포화나 전역 최적값을 확인했다고 하지 않는다.

### 단계별 비교

1. 4KiB·16KiB 분산 초기 배치를 만들고 작은 주소 예제로 매핑과 sensing 재사용을 검증한다.
2. Offset·발행 시점 등 미결정 조건을 정하고 동일 논리 trace를 적용한다.
3. Buffer·Outstanding·tR·총 channel 수를 고정하고 Prefetch OFF/ON을 비교한다.
4. 각 활성 port 수에서 Outstanding 포화 구간을 탐색하고, 유망한 조건에서 버퍼 용량과 선행량을 한 축씩 변경한다.
5. 재배치·MQSim 유래 상태를 여러 seed로 평가한다. 처음부터 모든 조합을 전수 실행하지 않는다.

| 지표 | 기록할 내용 |
|---|---|
| 응답 지연 | 발행→첫 데이터, 발행→마지막 데이터. 평균·p95·p99와 표본 수 |
| 유효 대역폭 | Host 요청 데이터량 / 측정 시간. Port별·전체 |
| 지연 내역 | 조회·큐 대기·sensing·전송·반환. 중첩 구간은 단순 합산하지 않음 |
| Channel 활용 | Channel별 busy 시간, 대기, 부하 편향 |
| NAND 동작 | sensing 횟수, Short/Mid/Long/Group별 횟수 |
| 재사용 | Demand buffer hit, 진행 중 Read 병합, NAND page buffer hit, 재sensing을 구분 |
| Prefetch 효과 | 사용한 데이터, 미사용 데이터, 제시간에 준비되지 않은 요청 |
| 읽기량 | sensing 대상 bytes, NAND 전송 bytes, Host 요청 bytes를 각각 기록 |

측정 시작 시 data buffer가 cold인지 warm인지 명시한다. L2P가 사용 이력을 반영한다는 것과 data buffer가 warm이라는 것은 별개다. 재방문을 포함하면 단순 bytes 비율 외에, 가져온 데이터 중 한 번 이상 사용한 비율과 재사용 횟수도 구분한다.

각 실행에 코드 revision, 설정, trace, 배치 snapshot, seed, warmup 조건을 저장한다. 구현되지 않은 UCIe 상세까지 포함한 실기 End-to-End 성능으로 표시하지 않는다.

## 후속 튜닝과 실제 구현 정보 확인 항목

Prefetch 정확도는 100% 합성 기준선과 저하 조건을 비교하기로 확정했다. 구체적인 구간, 후보 예산, coverage, 오예측 주소 분포 및 선행 시간 범위는 추가 정의한다.

1. B계열의 구체적인 offset. B-3는 재방문 시 다른 위치를 읽는 조건으로 확정.
2. Port별 비중첩·일부 중첩 영역 평가로 확정. 구체적인 중첩 비율과 발행 시간차는 추가 정의. Port 내부 strict in-order와 요청 간 응답 beat 비인터리빙은 확정. 4KiB는 단일 요청·조회 1회·credit 1개로 확정. Outstanding은 1부터 처리량 포화 구간까지 평가하기로 확정.
3. Die/LUN 구성과 추가 공유 자원 제약. Channel당 8 Plane, Plane 순환 배치, Plane 내부 E/O→SSL→Block→WL→Group 순서는 확정.
4. 활성 port당 16KiB 선두 Demand 보호는 확정. 선두 교체·병합·후속 요청 고정에 대한 admission 세부 규칙과 진행성 검증. 미사용 Prefetch는 공간 부족 시 적재 완료가 오래된 순서로 폐기하기로 확정. Controller 항목은 연결된 모든 Host 요청 반환 후 해제하며 NAND page buffer는 별도 유지. 캐시는 추후 판단.
5. 최초 sensing은 Plane별 20.69μs, 이후 주소 이력도 Plane별 관리로 확정. Page buffer 무효화 등 예외적인 재sensing 규칙은 필요 시 별도 정의.
6. L2P 사전 상태 생성 조건과 MQSim 추출 방식.
7. Plane 내부 작업의 점유 길이·분포·상관관계와 경계 처리, page buffer 접근·유효성 정책. 가용 시간 85%는 확정.
8. Read 명령 CA 점유는 100ns로 확정. Page buffer 데이터 출력 등 추가 명령 비용은 별도 확인. CA는 발행 가능한 Demand 우선·대기 순서·Busy Plane 우회, Data는 Demand 우선·준비 순서·비선점으로 확정.

### 버퍼 admission의 추가 구현 가정

이전 선두가 완료된 뒤에도 병합된 후속 요청이 페이지를 고정하면, 단순히 선두당 한 페이지 여유만 예약하는 것으로 진행성을 보장하기 어렵다. 새 모델은 Host 수락 시 필요한 물리 페이지의 공간 credit을 예약하고 같은 페이지 요청끼리 공유한다. 다른 port의 새로운 선두를 위한 여유도 보호한다. 공간이 부족하면 수락을 지연하고 그 시간을 별도 기록한다.

## 높은 QD의 Host-only 성능 기준

사용자 방향: “PF를 high QD에서는 꺼야 하지 않을까? 결국 host 요청만으로 성능이 최대가 나와야 하거든.” 이후 높은 QD 성능 튜닝은 `prefetch=false`를 기준선으로 삼는다. PF는 같은 자원·배치·정책의 ON/OFF 추가 효과로 평가한다. 기존 `pf_ahead_limit=0`은 PF 자체를 끈 것이 아니므로 설정 이름을 구분한다.

4port·32MiB에서 A1/A2 × QD128/1,024/2,048/4,096/8,192 × PF OFF/ON을 비교하고, QD2,048에서 긴 요청열과 64Plane을 확인했다. [총 28개 조건](../results/znand/pf_qd/RESULTS_KO.md)은 신규 18개와 이전 동일 조건 대조군 10개다. 각 쌍은 `prefetch` Boolean만 다르며 기존 CA 정책·port 내부 in-order·NAND 값은 유지한다.

기본 32Plane·8,192요청/port에서 PF OFF 관측 최고는 두 패턴 모두 **QD2,048/port**로, A1 133.772GB/s, A2 137.212GB/s였다. 같은 조건의 ON은 134.339/135.035GB/s다. QD4,096·8,192에서는 두 패턴 모두 OFF가 빠르지만, OFF에서도 QD2,048보다 낮았다. QD를 높이거나 PF를 끄는 것만으로 전체 병목이 해결된 결과는 아니다.

기본 A1의 QD2,048에서 PF ON의 Host 측정 구간 이득은 약 0.42%다. PF 사전 NAND 작업 시간을 포함한 ON은 133.008GB/s로 OFF 133.772GB/s보다 낮다. 반면 긴 A1에서는 사전 시간을 포함해도 ON이 빠른 조건이 남는다. 두 측정 구간과 요청 길이를 함께 기록하고, 공통 QD cutoff를 확정하지 않는다.

다음 구현 비교는 Host-only 상태에서 요청 메타데이터와 payload 예약을 분리하고, 실제 수락량과 Plane별 발행 가능한 물리 페이지 수를 관측한다. 많은 4KiB/64B 요청이 같은 16KiB 페이지를 공유할 수 있으므로 설정 QD를 NAND 병렬성으로 직접 환산하지 않는다. 동적 PF OFF/ON을 추가한다면 실제 Demand 가시성·Plane별 준비 작업·버퍼 상태에 따른 기준과 전환 시 이미 진행 중인 PF 처리 방법을 따로 검증한다. 이번 실행은 정적 ON/OFF 비교이며 자동 전환 기능은 추가하지 않았다.

## Host IF 목표의 물리 가능성과 배치 비교

후속 [물리 상한 검토와 12개 진단](../results/znand/host_ceiling/RESULTS_KO.md)으로 튜닝 목표를 geometry별로 구분한다. 현재 Plane 점유 규칙에서 32Plane은 최단 tR·내부 점유 제거 조건에서도 222.674GB/s다. 85% 가용률과 Short/Mid 교대를 반영한 지속 공급량 근사는 약 186.111GB/s다. 256GB/s 달성을 32Plane 스케줄러의 목표로 두지 않는다.

기존 snapshot 기능으로 각 논리 주소 영역이 모든 channel을 사용하면서 각 channel 안의 별도 Plane 그룹에 놓이도록 재배치했다. 요청별 channel·offset과 물리 페이지 1:1 대응은 보존했다. PF OFF·실제 지연·in-order에서 A1/A2 전체 처리량은 32Plane 177.115/174.788GB/s, 64Plane 236.361/234.988GB/s다. 64Plane 중간 완료 구간은 약 255GB/s였지만 장시간 지속값은 아직 확정하지 않는다.

후속 알고리즘·배치 튜닝의 기준 tR는 **First 20.69 / Short 2.00 / Mid 2.08 / Long 12.16 / Group 20.69μs**다. 이번 네 배치 비교는 같은 geometry 내에서 `snapshot`만 변경했으며, 평균 tR 감소는 고정된 종류별 시간에 대한 발생 빈도 변화다. 성능 표에는 tR 입력값과 함께 종류별 횟수·가중 평균을 기록한다. tR 또는 가용률을 바꾸는 사양 민감도 실험은 별도 대조군으로 분리하고, 기존 조건의 알고리즘 향상률에 섞지 않는다. [최종 대조 검증](../results/znand/host_ceiling/timing_validation.json)에 네 쌍의 설정 차이와 12개 실행의 입력 일치를 저장했다.

이번 배치는 네 주소 영역의 균형 부하에 맞춘 정적 실험이다. Port와 channel의 고정 1:1 연결이나 runtime 미래 예측을 추가하지 않았다. 한 영역에 부하가 몰리거나 실제 L2P가 변경되는 조건에서의 성능은 남아 있다. 기존 A2 trace의 경계를 공유하는 요청 3개도 그대로 보존했다. 합성 snapshot을 MQSim 또는 실제 SSD 배치로 취급하지 않는다.

다음 평가 순서는 (1) 32/64Plane별 물리 목표 결정, (2) 주소 영역 배치 효과의 장시간·다른 seed·부하 편향·L2P 민감도, (3) 동일 geometry·배치에서 예약/admission 조정으로 남은 손실 분리다. 64Plane에서는 Data turnaround 포함 상한 257.496GB/s가 Host 256GB/s에 매우 가까우므로 channel별 전송 공백도 함께 계측한다. 현재 8,192요청/port의 cold 전체 평균은 최초 준비 지연만 반영해도 Host 경로 상한이 약 245.805GB/s임을 함께 표시한다.

## 64Plane을 기준으로 한 후속 측정

사용자 요청에 따라 이후 성능 평가 geometry는 **4channel × 16Plane = 총 64Plane**으로 둔다. [64Plane 측정](../results/znand/planes64/RESULTS_KO.md)은 tR·가용률·버퍼·QD·발행 정책을 고정하고 A1/A2의 기존 배치와 영역 배치를 모두 새로 실행한다. 8,192요청/port를 재현하고 32,768요청/port까지 늘린다. 정적 snapshot은 각 길이에 맞춰 생성하며 모든 배치 쌍에서 channel·offset과 요청열을 유지한다.

이후 튜닝의 기본 비교 단위는 동일한 64Plane·요청 길이·물리 배치다. 요청 수 확대 시 기존 workload의 논리 영역 span도 커지므로 짧은 실행과 긴 실행의 차이를 startup 영향만으로 설명하지 않는다. 기존 배치는 Plane 확장만의 효과를 확인하는 대조군이며, 영역 배치는 균형 부하를 이용하는 배치 조건으로 구분한다. 이번 결과로 64B 패턴·write 혼합·실제 동적 L2P의 성능을 추정하지 않는다.

## 64Plane Controller buffer 16MiB 비교

[16MiB 비교 결과](../results/znand/planes64_buffer16/RESULTS_KO.md)는 `buffer_pages`만 2,048→1,024로 줄인 신규 8개 조건과 동일 모델의 32MiB 대조군 8개를 대조했다. tR·QD·PF OFF·주소 배치·스케줄링 정책은 유지했다. 개선 배치의 A1/A2 × 8,192/32,768요청/port 네 쌍은 처리량뿐 아니라 지연·Long·점유 계측까지 정확히 같았다. 긴 실행의 전체 처리량은 249.508/249.325GB/s이며 peak 예약량은 12.016/11.750MiB다.

기존 배치의 긴 A1/A2는 32→16MiB에서 210.574→132.934GB/s (−36.87%), 214.082→128.185GB/s (−40.12%)로 감소했다. Long 비율도 12.8448→28.9825%, 12.3703→18.9178%로 증가했다. 용량이 Host 수락 단계의 예약 공간을 제한하므로 실제로 수락한 요청과 발행 후보가 달라진다. 따라서 개선 배치에서 확인한 16MiB 여유를 기존 배치까지 적용하지 않는다.

16MiB 프로파일은 별도로 제공하고 기존 32MiB 기준은 보존한다. 이후 용량 축소 여부는 배치를 고정한 상태에서 긴 요청열·부하 편향·다른 seed·활성 port 수를 함께 검증한다. 회사에서 실행한 더 큰 요청 수는 정확한 조건과 원본 결과가 아직 확보되지 않았으므로 이번 16MiB 검증 범위에 포함하지 않는다.

## 개선 배치에서 200GB/s를 유지하는 버퍼 하한

[버퍼 하한 측정](../results/znand/planes64_buffer_floor/RESULTS_KO.md)은 공유 controller buffer만 1/2/4/6/7/7.25/7.5/7.75/8/10/12/16/32MiB로 바꿨다. 64Plane, 4port, QD2,048/port, PF OFF, 기존 tR·가용률·snapshot·발행 정책을 유지했다. A1/A2 × 8,192/32,768요청/port의 신규 44개와 검증된 16/32MiB 대조군 8개를 사용했다.

시작부터 종료까지의 전체 평균이 네 조건 모두 200GB/s 이상인 최소 측정 용량은 **7.75MiB(16KiB 슬롯 496개)**다. 경계는 0.25MiB 간격으로 확인했으며, 모든 슬롯 수를 전수 탐색한 절대 하한은 아니다. 긴 A1/A2는 214.678/215.186GB/s, 짧은 A1/A2는 206.530/208.675GB/s다. 바로 아래 7.5MiB는 긴 A2만 201.866GB/s로 통과하고 나머지 세 조건은 189.137~196.182GB/s로 미달했다.

현재 조건에서 200GB/s 목표의 용량 후보는 **공유 8MiB(512슬롯)**다. 긴 A1/A2는 236.348/223.187GB/s, 짧은 A1/A2는 225.014/217.521GB/s다. **10MiB(640슬롯)**에서는 긴 A1/A2가 249.367/248.610GB/s로 기존 16MiB의 249.508/249.325GB/s에 근접한다. 이번 결과만으로 모델 기본 용량을 변경하지 않으며, 모든 workload에서 유지되는 제품 사양으로 확정하지 않는다.

작은 버퍼의 성능 저하는 Long 증가만으로 설명되지 않는다. A1은 모든 용량에서 Long=0이며, 긴 A2의 7~16MiB도 Long=4회다. 현재 모델은 수락 시 공간을 예약하고, admission이 매번 Port 0→1→2→3 순서로 시도한다. 7.5MiB의 긴 A1에서 Port 0~2는 약 2.13ms에 완료하지만 Port 3는 2.742ms까지 걸린다. 전체 200GB/s를 위한 마지막 반환 시한 2.684ms를 넘는 것이 최종 미달로 이어진다. 이 관측은 공유 버퍼 수락 경쟁과 Plane 그룹별 진행 불균형을 후속 조사할 근거다. 특정 정책의 독립적 인과 효과는 대조 실험이 필요하다.

후속 튜닝은 (1) 고정 Port 순회와 round-robin admission 비교, (2) port별 최소 예약량과 공유 여유 공간의 균형, (3) 요청 메타데이터와 payload 예약의 분리 순서로 검토한다. Port 내부 in-order, 공유 페이지의 단일 예약, 선두 진행성 보장, 총 버퍼 한도를 유지하며 동일 배치·용량·요청열로 비교한다. 이번 측정에서는 이 정책들을 구현하거나 변경하지 않았다. 선정 용량의 다른 seed·부하 편향·실제 동적 L2P 검증도 남아 있다.

## 처리량 판정 기준 변경: 지속 부하와 실제 Device outstanding

사용자는 전체 명령 처리 완료 시간을 기준으로 삼는 대신, Device에 실제로 outstanding된 요청을 유지해 최대 성능 구간을 만들고 그 구간의 평균과 시간 변화를 보도록 요청했다. 이후 처리량 평가의 주 기준은 [지속 부하 측정](../results/znand/saturation/RESULTS_KO.md)으로 둔다. 기존 finite-trace 전체 완료 평균은 별도 지표로 보존하며 7.75MiB 하한을 새 기준에 그대로 적용하지 않는다.

Device outstanding은 **AR 수락부터 마지막 응답 완료까지**다. Port마다 다음 Host 명령을 항상 제시하며 기존 device admission/QD 제한으로 수락 여부를 결정한다. 수락 시 다음 주소로 보충하고, 반환으로 QD 슬롯이 비면 다시 수락할 수 있다. Host pending은 Device outstanding에 더하지 않는다. 새로운 source는 기존 요청 채널의 최대 1요청/ns/Port를 활용하며, 데이터 반환은 기존 64GB/s/Port 제한을 유지한다. 유한 입력의 offer 간격과는 다른 부하 방식이다.

관측은 첫 요청부터 2.2ms에 종료하고 미완료 요청을 drain하지 않는다. 초기 200µs를 제외한 **고정 2ms 평균**과, 그 안에서 25µs 간격으로 찾은 **최고 연속 500µs 평균**을 함께 기록한다. 500µs는 5개 maintenance 주기, 2ms는 20개 주기다. 시간 그래프와 CSV는 25µs별 payload 전송률, 수락/완료 요청 수, 누적 요청 수, Port별 실제 outstanding 평균/최소/최대/끝값과 버퍼 점유를 제공한다. 최고 구간의 시작/종료와 완료 요청 수도 명시한다.

42개 조합의 측정 결과는 다음과 같다. tR·NAND geometry·PF OFF·가용률·Port 내부 순서와 기존 수락/발행 정책은 그대로다.

| 버퍼 | 선택 QD/Port | A1 고정 2ms / 최고 500µs GB/s | A2 고정 2ms / 최고 500µs GB/s |
|---|---:|---:|---:|
| 3MiB | 192 | 191.313 / 192.004 | 197.337 / 198.131 |
| 4MiB | 256 | 234.484 / 235.289 | 239.904 / 240.745 |
| 8MiB | 512 | 255.366 / 255.659 | 255.058 / 255.607 |
| 16MiB | 512 | 255.372 / 255.820 | 255.211 / 255.653 |

8MiB·QD512/Port의 실제 outstanding 총합 평균은 A1 2,006.7개, A2 2,035.9개다. A1 Port별 값은 511.4/510.6/510.3/474.5개, A2는 512.0/511.8/511.4/500.8개다. 이 구간의 처리량은 네 Port가 각각 약 64GB/s를 내며 유지된다. A1 최고 구간 900~1,400µs에서 완료 31,208개, A2 600~1,100µs에서 31,203개를 기록했다. 고정 2ms의 전반/후반 평균 변화는 각각 +0.042%, −0.151%였다.

같은 8MiB에서 QD2,048/Port를 허용하면 A1 실제 Port별 outstanding은 2,026.5/1/1/1개로 편중되고 고정 평균은 68.858GB/s다. A2도 2,033.8/2.6/2.5/2.5개, 71.889GB/s였다. 총 outstanding이 약 2천 개로 비슷해도 Port 분포가 다르면 성능이 크게 달라진다. 이 결과는 현재 고정 순회 admission과 수락 시 공유 버퍼 예약 정책을 반영하며, 큰 QD 자체가 모든 장치에서 불리하다는 뜻은 아니다.

새 측정 코드는 원본 model.py를 변경하지 않는 Host 공급/관측용 harness다. mapping 도메인은 65,536요청/Port를 담을 수 있도록 확장했지만 이 요청 수를 끝내는 실험은 아니며, 첫 32,766요청/Port의 실제 물리 위치와 offset이 이전 개선 배치와 같음을 검증했다. 모든 실행은 주소 도메인을 소진하기 전에 종료했다. 향후 기본 비교는 8MiB·QD512의 지속 부하를 대표 조건으로 사용하되, 공정 admission·payload 예약 분리·다른 seed·부하 편향·더 긴 시간은 추가 검증 대상으로 둔다.


## B1/B2 부분 읽기: 지속 부하와 유효 데이터 비율 (2026-10-11)

[B1/B2 지속 부하 실험](../results/znand/partial_saturation/RESULTS_KO.md)은 64B 부분 읽기도 같은 200µs warm-up 제외·고정 2ms·최고 연속 500µs 기준으로 평가한다. B1은 4KiB 논리 페이지의 첫 64B를 1→2→3 순서로, B2는 1→3→2의 국소 순열로 읽는다. 같은 페이지 안에서 64B씩 연속 읽는 부하는 아니다.

버퍼 4/8/16MiB × QD128/256/512/1024/2048 per port × B1/B2의 30개 조건을 실행한다. 두 패턴 모두 직전 A1의 4KiB stripe·개선 영역 배치·head_locality/bypass32/head_wait48.64µs를 사용해 장치 설정을 통일한다. 과거 B 전용 locality 설정과 혼합하지 않는다. tR, 64Plane, PF OFF, 가용률 85%, 16KiB 전체 NAND 출력, port 내부 in-order와 공유 버퍼 예약 정책은 유지한다.

| 버퍼·QD/port | B1 고정 2ms / 최고 500µs GB/s | B2 고정 2ms / 최고 500µs GB/s |
|---|---:|---:|
| 4MiB·256 | 3.962 / 3.978 | 3.952 / 3.963 |
| 8MiB·256 | 3.983 / 4.000 | 3.979 / 3.989 |
| 8MiB·512 | 3.995 / 4.014 | 4.001 / 4.031 |
| 8MiB·1024 | 2.941 / 2.974 | 3.206 / 3.220 |

8MiB·QD512/port의 고정 구간 완료 수는 B1 124,832개, B2 125,023개이며 약 62.4/62.5MIOPS다. 실제 outstanding 합계 평균은 2,030.7/2,029.3개, 내부 NAND 전송은 256.778/256.991GB/s다. 해당 구간에서 Long sensing은 둘 다 0회다. QD를 더 늘릴 때의 저하는 현재 공유 예약과 port 분포를 함께 해석해야 한다.

16KiB 물리 페이지 안의 네 4KiB 영역에서 각각 64B만 사용하면 Host 유효 데이터는 256B다. 최적 병합에서도 유효 비율은 1.5625%이며, NAND Data의 전송·turnaround만 고려한 장기 상한 257.496GB/s를 Host 데이터로 환산하면 약 4.0234GB/s다. 짧은 구간에는 이전에 준비한 데이터 방출이 있어 일시적으로 이를 넘을 수 있다. 실제 구간의 데이터량은 완료 이벤트로 따로 집계하며 경계의 in-flight 차이·재전송 때문에 정확히 64배가 아닐 수 있다.

후속 튜닝의 판단 순서는 다음과 같다.

1. 현재 전체 페이지 출력 모델에서는 4MiB·QD256부터 약 4GB/s에 근접한다. 버퍼·QD 증가의 작은 이득과 불균형 위험을 함께 비교한다.
2. 더 큰 유효 처리량은 부분 NAND 출력의 지원 단위, CA/column-change 비용, ECC 최소 처리 단위를 정의한 뒤 별도 모델로 검증한다. 64B만 전송하면 tR까지 1/256로 줄어드는 것으로 가정하지 않는다.
3. 같은 물리 페이지의 연속 64B 요청을 많이 읽는 별도 workload를 추가하면 준비한 데이터의 재사용률을 평가할 수 있다. 원문의 B1/B2와 구분한다.
4. 64B 단위 L2P 분산은 기존 사용자 제외 결정을 유지한다. 공정 admission, cache ON/OFF, 다른 seed·장시간·불균등 부하는 별도 대조 실험으로 남긴다.


### B 파형의 주기적 낙폭 진단

[Maintenance 대조 6개](../results/znand/partial_dips/RESULTS_KO.md)에서 8MiB·QD512/port·기존 tR·in-order를 고정하고 가용률 OFF 대조와 200µs 주기 대조를 수행했다. 기준의 100µs 주기/Plane당 명목 15µs off가 선두 데이터 준비를 지연시키고 후속 ready 응답도 함께 멈추게 했다. B1 실제 사례에서는 699.288–717.676µs의 선두 정지 중간에 후속 227개 요청이 이미 준비돼 있었다. sensing은 Mid 2.08µs였고, 선두 대기 중 14.736µs는 해당 Plane maintenance와 직접 겹쳤다.

200–1,200µs의 고정 1ms에서 B1의 25µs 처리량 범위는 기준 2.619–4.854GB/s, maintenance OFF 대조 4.014–4.055GB/s였다. B2도 2.627–4.680에서 4.009–4.063GB/s로 큰 주기적 낙폭이 사라졌다. 기준 두 실행의 첫 1.2ms 계측은 이전 B 실험과 일치한다. 진단용 OFF 설정을 기본값으로 채택하지 않는다.

후속 비효율 모델은 평균 85% 외에도 off 지속시간·도착 간격·Plane 간 상관·공유 채널 영향을 분리한다. 현재는 seed별 Plane 위상을 가진 주기적 off 모델이며 실제 GC 작업열이 아니다. 같은 평균 가용률이라도 짧은 구간 파형은 달라질 수 있다. 사용자 조건인 in-order를 유지하면서 선두·가까운 미래 요청의 준비 우선순위와 반환 가능 데이터량을 함께 평가한다.
