# 질문별 의도와 답변 조건

**명칭 안내:** 이 문서의 기존 B1/B2/B3(또는 B-1/B-2/B-3)는 현재 C1/C2/C3에 해당합니다. 새 B는 페이지 내부 64B 연속 읽기입니다. [현재 정의](15_workload_naming_ko.md)를 참고하세요. 원문 질의·과거 재현 명령은 당시 표기를 유지합니다.

아래는 [영문 질문](01_questions_en.md)에 근거한 해석입니다. HBF 조사 결과나 특정 제품의 구현을 질문 원문에 역으로 끼워 넣지 않습니다.

## 1. 실제 읽기 지연시간은 무엇에 좌우되는가?

### 1-1. End-to-End의 시작과 끝

UCIe request channel에서 요청을 발행한 시점부터 데이터 반환까지를 묻습니다. NAND 내부 시간만으로 답변할 수 없습니다.

추가로 맞춰야 할 기준은 첫 데이터 도착인지 전체 데이터 반환 완료인지, 요청 발행인지 수락인지, 요청 대기가 있는 상태인지입니다.

### 1-2. UCIe·controller·NAND 구간 분해

전체 시간 중 어디가 지배적인지, 요청 방식이나 인터페이스를 바꾸면 어느 부분을 줄일 수 있는지 확인하려는 질문입니다. 작업들이 겹쳐 진행된다면 각 단계의 시간을 단순 합산하지 말고 실제 critical path를 보여줘야 합니다.

### 1-3. Page switching/swapping

페이지를 바꿔 읽을 때 별도 비용이 있는지 묻습니다. 원문은 switching/swapping의 구체적인 내부 동작을 정의하지 않습니다. Buffer 교체, 새 sensing, 스케줄링 대기 등을 구분해서 설명할 필요가 있습니다.

### 1-4. 접근 패턴별 의미

| 패턴 | 직접 비교할 대상 | 핵심 질문 |
|---|---|---|
| A-1: 4KB, 1→2→3 | 기준 패턴 | 순서대로 읽는 요청의 지연은 얼마인가? |
| A-2: 4KB, 1→3→2 | A-1 | 읽는 순서를 바꾸면 비용이 생기는가? |
| B-1: 64B, 1→2→3 | A-1 | 읽는 양을 줄이면 내부 작업과 응답시간도 줄어드는가? |
| B-2: 64B, 1→3→2 | B-1, A-2 | 작은 데이터가 여러 페이지에 흩어져 있을 때 어떤가? |
| B-3: 64B, 1→3→1→2 | 첫 번째와 두 번째 Page 1 | 다른 페이지를 거친 뒤에도 기존 데이터를 재사용하는가? |

페이지 번호만으로 물리 배치를 알 수 없습니다. 접근 순서의 효과를 비교하려면 bank·die·channel 배치를 함께 고정해야 합니다. 화살표만으로 요청들이 직렬인지 동시 발행인지도 알 수 없습니다.

B-1/B-2는 각 페이지에서 64B씩 읽는 예시입니다. 한 페이지 전체를 64B씩 모두 읽는 실험과 다릅니다. B-3에서는 같은 물리 페이지인지와 재방문 offset을 추가로 명시해야 합니다.

### 1-5. 두 IO 모드

동일 주소·길이·요청 시점·부하에서 IO 모드를 바꿨을 때 지연이 달라지는지 묻습니다. 두 모드의 요청 경로와 완료 의미부터 일치시킨 뒤 비교해야 합니다. Prefetch ON/OFF와는 다른 축입니다.

## 2. 어떤 요청이 허용되고, 수신 중 어떻게 흐름을 제어하는가?

### 2-1. 주소 정렬

요청의 시작 위치를 얼마나 세밀하게 지정할 수 있는지 묻습니다. 예를 들어 `0x1000`과 `0x1040`은 모두 64B 정렬이지만 두 번째는 4KB 정렬이 아닙니다. 작은 요청 길이 지원과 작은 단위의 시작 주소 지원은 별개입니다.

### 2-2. Burst 길이

64B부터 4KB까지 어떤 길이를 지원하는지 묻습니다. 192B가 예시에 포함되어 있으므로 2의 거듭제곱 길이뿐 아니라 64B 배수 길이의 지원 여부가 중요합니다.

4KiB를 64B 요청으로 나누면 64개 요청이고, 하나의 4KiB 요청이면 1개입니다. 요청마다 비용이 있다면 조회 횟수와 outstanding 개수의 의미가 달라집니다.

### 2-3. Sub-4KB 비용과 제한

지원 여부와 성능 효율은 다릅니다. 고정 처리비용, 요청 병합, 최소 내부 작업 단위, 작은 요청의 지속 처리율을 확인해야 합니다.

### 2-4. Back-pressure

4KB 일부를 받은 후 멈추고 재개할 수 있는지, 현재 burst를 모두 받은 다음에만 대기시킬 수 있는지 묻습니다. 어떤 계층의 READY인지, 멈춤이 전달될 때까지 도착하는 데이터를 어디에 보관하는지가 중요합니다.

## 3. 병렬 자원을 활용하려면 어떤 주소들을 읽어야 하는가?

### 3-1. 색칠된 블록의 크기

그림의 블록 하나가 몇 byte인지 알아야 주소 증가에 따라 어떤 자원으로 이동하는지 계산할 수 있습니다. 삼성의 해당 그림은 이번 이미지에 포함돼 있지 않습니다.

### 3-2. 단일 die 또는 여러 die 분산

하나의 요청이 점유하는 자원 범위를 묻습니다. 요청 하나가 여러 die를 함께 사용하는 구조와, 여러 요청을 다른 die에 분산하는 구조는 병렬성의 의미가 다릅니다.

### 3-3. 4KB 인터리빙 그림

요청 주소를 4개 채널에 분산하여 전체 대역폭을 활용하려는 목적이 명시되어 있습니다. 주소 분산뿐 아니라 충분한 동시 요청과 반환 경로의 처리 능력도 실험 조건으로 기록해야 합니다.

Port·UCIe channel·NAND channel·die·bank의 이름을 혼용하지 않습니다. 이번 설계에서 사용자에게 확인된 것은 4개의 독립 port이며, 원문에 등장하는 4개 channel과의 정확한 연결은 별도로 정의해야 합니다.

## 4. 호스트가 어디까지 관리해야 하는가?

### 4-1. Queue·global address·block 관리

호스트가 단순히 주소와 크기를 전달하는지, 내부 자원을 알고 스케줄링·할당·erase까지 관리해야 하는지 범위를 구체화하려는 질문입니다. 각 기능의 주체와 필요한 정보를 표로 답하는 것이 적절합니다.

### 4-2. L2P

장치에 전달하는 주소가 논리 주소인지, 호스트가 실제 물리 위치를 찾아 전달해야 하는지 묻습니다. 주소를 알아내는 비용과 책임이 어디에 있는지에 관한 질문입니다.

Prefetch hit 조회와 L2P 변환은 별도 기능입니다. 하나의 지연 항으로 합치려면 실제 경로에 대한 근거가 있어야 합니다.

### 4-3. Wear leveling·bad block·repair

제목과 문장 앞부분만 확인됩니다. 관리 기능을 장치가 내부적으로 처리하는지 묻는 방향은 읽을 수 있지만, 잘린 세부 질문을 복원해서 원문으로 제시하지 않습니다.

## Read/write 혼합 문의에 대한 범위

보이는 영문 1~4번에는 혼합 read/write를 직접 묻는 문장이 없습니다. 한국어 메모의 §5 언급은 별도 문서에 대한 요약이므로 누락된 영문 질문을 대신하지 않습니다. HBF 자체의 혼합 동작은 [조사 결과](03_hbf_findings_ko.md)에서 별도로 확인했습니다.
